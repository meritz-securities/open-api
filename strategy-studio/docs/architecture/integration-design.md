# 통합 설계 초안

고객 PC에서 Studio / 기존 MCP / CLI가 동일 StrategyRuntime 서비스를 호출한다. Runtime은 schema 검증 → 읽기전용 데이터 snapshot → DSL evaluator 또는 격리 Python worker → 기존 host broker → 결정론 분석 → SQLite 저장의 순서로 처리한다.

- Studio는 loopback 서버의 좁은 action API를 사용한다. API는 고정 Host/Origin, 무작위 session token, body/실행량 제한을 적용한다.
- 기존 MCP에는 실제 구현된 플랫폼 도구만 추가한다. 시세·계좌·주문 도구 계약과 보호 규칙을 유지한다.
- 선언형 DSL은 유한한 JSON 문법을 해석하며 eval·임의 import·파일·네트워크를 제공하지 않는다. Windows DSL 지원과 임의 Python 지원 상태를 분리한다.
- 데이터 hash·전략 hash·엔진 버전·비용·시드로 실행을 식별한다. 조회 계정명·키·토큰은 결과 provenance와 export에서 제외한다.
- 전략 revision과 실행 결과는 immutable snapshot이다. What-if/개선안은 parent ID로 연결하고 동일 snapshot을 재계산한다. 나빠진 후보도 보관한다.
- 자연어의 지능적 생성은 실제 연결된 Claude/MCP host가 담당한다. Studio에 LLM이 연결되지 않았다면 AI 생성으로 가장하지 않고 DSL/코드 import와 템플릿을 제공한다.
- Windows native 격리, 실제 해외3년 시세, 서명·공증·신규설치가 검증되기 전 정식 v1 완료로 선언하지 않는다.

공통 schema와 세 AI 검토 결과를 반영한 최종 계약은 technical-decisions 및 contracts 문서에서 고정한다.

## 기간을 나눠 개선·검증하는 실행 흐름

Studio·MCP·CLI는 `runtime/research.py`의 같은 실행 흐름을 사용합니다. 별도 중앙 계산 서버를 추가하지 않습니다. 시세 조회는 기존 메리츠 어댑터를 재사용하고, 아래 처리는 고객 PC에 저장된 시세 사본으로 수행합니다.

1. 저장된 전략·시세·비용 설정 또는 기존 실행을 원본으로 지정합니다. 생성 단계에서는 기간과 해시, 실행 식별자를 저장하며 계산하지 않습니다.
2. 앞 기간에서 원본을 한 번 계산하고 그 결과에만 연결된 AI 개선 요청을 만듭니다. 기존 CLI·HTTP AI 경로는 앞 기간의 계산 결과를 사용합니다.
3. 제출한 개선안 전체가 성공하면 앞 기간 수익률로 원본 또는 개선안 하나를 확정합니다. 동률은 원본, 제출 순서로 결정합니다.
4. 확정 후 뒤 기간에서 원본과 선택된 전략만 계산합니다. 뒤 기간 결과로 선택을 바꾸지 않으며, 각 기간은 초기 자금과 빈 보유 상태에서 독립적으로 시작합니다.
5. 확정·취소, 결과 완료·취소는 짧은 SQLite 트랜잭션에서 순서를 결정합니다. 먼저 확정된 결정에 맞춰 응답하며 이미 저장된 개별 계산은 보존합니다.
6. 정상 취소·시간 초과는 최종 기록을 남깁니다. 갑작스러운 프로세스 종료나 저장 실패로 최종 기록을 못 남긴 경우에는 예약된 개별 실행 기록으로 상태를 복원하고 자동 재실행하지 않습니다.

현재 이 흐름은 조건식 전략을 지원합니다. 전체 4~5,000봉, 개선 기간 비율 20~80%, 각 기간 최소 2봉이어야 합니다. 원본 1회와 개선안 최대 3회를 앞 기간에 실행하고, 뒤 기간은 최대 2회 실행합니다. 기간 분리는 사용자가 뒤 기간을 과거에 보지 않았음을 보장하지 않습니다. 기존 전체 실행과 반복 사용 이력도 함께 표시합니다.

고객용 Studio에서는 후보 제출이 MCP 경로(`meritz_ai_candidates_submit`)로만 들어오며, Studio 안의 AI 패널은 노출되지 않습니다. 기간 분리 작업 자체는 Studio·CLI·MCP(`meritz_research_*`)에서 같은 Runtime으로 실행합니다.
